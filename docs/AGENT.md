# Agent 开发者指南

> 本文档面向参与本项目的开发者与 AI 协作者，约定工作流程、代码规范、文档更新与汇报要求。

## 工作流程

1. **文档优先**：提出新方案或改动既有设计后，先更新相关文档（尤其是 `docs/ARCHITECTURE.md`），再改代码。
2. **先理解需求**：动手前先阅读相关文档（README、ARCHITECTURE、当前模块说明），确认目标与边界。
3. **测试驱动**：需要测试时，先写（或同步写）测试用例。
4. **先设计后编码**：写代码前说明计划（做什么、怎么做、预期输入输出），等待确认后再开始。
5. **边做边记**：把关键决策、遇到的问题、临时 TODO 记录到 `docs/NOTE.md`。
6. **小步提交**：完成一个可验证的小步骤后提交，提交信息清晰描述改动。

## 注意事项

- **不要自动执行 Git 操作**：如 `git add`、`git commit`、`git push`。先征求开发者确认。
- **不要自动执行系统级操作**：如安装软件、修改系统配置。应放在 Dockerfile 或明确指定的脚本中。
- **及时沟通不确定项**：需求或技术选型不清晰时先问，不要臆测。
- **保持代码简单**：不要过度设计。可读性和能跑通是首要目标。
- **测试后再交付**：汇报进度时说明运行了哪些测试及其结果。
- **文档保持同步**：设计、接口、数据结构变更必须同步更新文档。文档是沟通的桥梁，必须准确。

## 开发流程

### 标准流程

```text
1. 阅读相关文档
2. 编写测试用例（单元 / 集成）
3. 实现功能
4. 运行测试并确保通过
5. 更新相关文档（如有变更）
6. 汇报进度
7. 等待用户确认后再提交（git commit）
```

### 代码规范

> 以下为初稿，随架构确定继续完善；行为树的编写规范见 `docs/ARCHITECTURE.md`。

- **命名**
  - 目录、文件、函数、变量：`snake_case`
  - 类型、类、结构体：`PascalCase`
  - 成员变量：尾部下划线，如 `blackboard_`
  - 常量：`kPascalCase`
  - 宏：`SCREAMING_SNAKE_CASE`
- **格式**：统一使用 clang-format，提交前不得残留格式差异。
- **注释**：ROS 2 包、节点、行为树节点需说明用途；复杂决策分支必须写明进入 / 退出条件与抢占关系。
- **日志**：统一使用项目日志接口，禁止散落的 `std::cout` 与原始 `RCLCPP_*` 调用；日志分级为 DEBUG / INFO / ACT / WARN / ERROR。
- **状态**：禁止新增全局可变状态；所有决策状态必须显式、可观测。

### Git 提交规范

格式：

```text
<type>(<scope>): <subject>

[可选正文]

[可选脚注]
```

**type**：

- `feat`：新功能
- `fix`：缺陷修复
- `docs`：文档更新
- `test`：测试相关
- `refactor`：重构
- `chore`：构建 / 工具配置

提交信息使用中文，一行简明描述改动。正文可选，分点并注意简明意赅。脚注可选，用于标记关联的 issue、PR 或其他信息。

**示例**：`feat(io): 新增裁判系统订阅与位段解码`
